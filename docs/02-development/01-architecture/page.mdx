# Architecture

Dependency Links has one VS Code extension-host runtime and multiple browser webview runtimes.

## Runtime layout

```text
Extension host
├── document links
├── workspace manifest discovery
├── source reference scanning
├── package-lock version lookup
└── webview panels
    ├── Inspector
    └── Dependency Explorer

Browser-safe shared code
├── src/shared/
├── src/utils/
└── src/webview-ui/
```

The extension host owns VS Code APIs and workspace file access. Browser-safe parsing, npm metadata resolution, graph shaping, filtering, and version-status helpers live outside the extension host so they can be unit tested directly.

## Extension host

The VS Code entry point is:

```text
src/extension/extension.ts
```

It is responsible for:

- registering JSON/JSONC/YAML dependency document links
- registering Inspector and Dependency Explorer commands
- creating webview panels
- resolving editor document links
- scanning workspace package manifests
- finding source references
- reading installed versions from package locks
- opening source references at their VS Code location

Panel creation and the webview message bridge live under:

```text
src/extension/webview-panel/
```

## Dependency parsing and resolution

Browser-safe utilities live under:

```text
src/utils/
├── parse.ts
├── resolve.ts
├── source-dependencies.ts
├── impact.ts
├── filters.ts
├── versions.ts
└── index.ts
```

### Manifest parsing

`parse.ts` handles dependency sections in JSON and YAML plus npm package specifiers.

### npm metadata

`resolve.ts` resolves npm metadata, repository/homepage links, the latest registry version, and one-hop package dependency metadata.

### Source references

`source-dependencies.ts` wraps `parse-imports-exports` and normalizes its output into Dependency Links reference records.

The parser is kept behind Dependency Links types rather than exposed directly to the webview. This allows the parser implementation to change without changing the UI contract.

Source references currently include:

- ECMAScript imports
- TypeScript type imports
- dynamic `import()`
- CommonJS `require()`
- re-exports
- package subpath normalization
- scoped package normalization

Workspace scanning is implemented in:

```text
src/extension/source-references.ts
```

A parser failure for one source file is isolated so it does not abort the rest of the workspace scan.

## Workspace discovery

Workspace package manifests are discovered by:

```text
src/extension/workspace-manifests.ts
```

Each manifest is represented as a workspace scope. The explorer uses those scopes together with dependency section filters to reduce large graphs.

References are associated with the nearest package manifest so the same workspace scope can filter both graph data and source usage.

## Version context

Installed npm versions are resolved from the nearest usable `package-lock.json` by:

```text
src/extension/version-context.ts
```

Pure package-lock extraction and status classification live in:

```text
src/utils/versions.ts
```

Version inspection is read-only. Dependency Links does not install, update, remove, or rewrite package dependencies.

## Dependency Explorer

The explorer UI lives under:

```text
src/webview-ui/dependency-graph/
├── App.tsx
├── DependencyFlow.tsx
├── ExplorerSidebar.tsx
├── ExplorerBottomPanel.tsx
├── PackageDetails.tsx
└── graph.ts
```

The layout uses four synchronized surfaces:

1. workspace and dependency filters
2. the graph/package/reference primary view
3. selected-package details
4. references, dependents, dependencies, and version tabs

Package selection is shared across those surfaces.

React Flow owns graph interaction. A single click selects a package and updates the rest of the explorer. A double click opens the package repository or npm fallback when available.

## Webview messaging

Shared message contracts live in:

```text
src/shared/messages.ts
```

The explorer uses the message bridge for operations that require VS Code APIs:

- listing workspace manifests
- scanning references
- opening a reference in an editor
- reading installed package versions

npm registry resolution can still run from browser-safe utility code because the webview CSP permits HTTPS registry access.

## Build targets

The project has separate Vite configurations:

```text
vite.extension.config.ts
vite.webview.config.ts
```

The extension build bundles the extension-host runtime while keeping `vscode` external.

The webview build is multi-entry and produces browser assets for the Inspector and Dependency Explorer under:

```text
out/webview-ui/
```

Shared React and utility code can be extracted into common chunks.
