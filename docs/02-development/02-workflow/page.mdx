# Development Workflow

## Common commands

### Build everything

```bash
npm run build
```

This runs the clean, extension build, and webview build steps.

### Watch extension and webviews

```bash
npm run watch
```

The extension build and multi-entry webview build run concurrently.

### Full development environment

```bash
npm run dev
```

This starts:

```text
extension watcher
webview watcher
browser preview
VS Code Extension Development Host
```

Set `CODE_COMMAND` if your VS Code CLI is not available as `code`.

### Browser previews

```bash
npm run dev:preview
```

The preview server opens the Inspector by default. The available preview pages are:

```text
/previews/inspector.html
/previews/dependency-graph.html
```

Outside VS Code, the shared API wrapper provides an in-memory VS Code state shim. Dependency parsing and resolution still run through the same browser-safe `src/utils/` modules used by the real webviews.

### Type check

```bash
npm run typecheck
```

The extension and webview use separate TypeScript configurations.

### Lint

```bash
npm run lint
```

### Test

```bash
npm test
```

The `pretest` lifecycle runs build, lint, and type checking before the VS Code test runner.

## Dependency utility changes

Keep browser-safe parsing and resolution behavior under:

```text
src/utils/
├── parse.ts
├── resolve.ts
└── index.ts
```

Do not route pasted dependency input through the extension host. Both React webviews import the shared utilities directly.

When adding or changing dependency sections, update the parser and tests together.

## Webview changes

React UIs live under:

```text
src/webviews/
```

Use the VS Code API wrapper only for capabilities that actually cross the webview boundary, such as persisted webview state.

Do not duplicate package parsing or resolution logic in individual React applications.

## Document link changes

Document links are registered in `src/extension.ts` and created by helpers in `src/extension/document-links.ts`.

Keep document scanning inexpensive. Network metadata resolution should happen when a link is resolved, not while a document is scanned.

## Dependency architecture checks

Run:

```bash
npm run deps:check
```

The dependency-cruiser rules enforce the extension/webview/shared/utils runtime boundaries and reject circular or unresolved source dependencies.

Generate a Mermaid dependency diagram with:

```bash
npm run deps:graph
```

These commands use a pinned dependency-cruiser version through `npx`, so the repository does not need to carry dependency-cruiser's transitive packages in its extension development dependencies.
